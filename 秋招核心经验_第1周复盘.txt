二、项目实战经验详解（本周STM32G431 FreeRTOS多传感器采集终端）

【项目概述】
硬件平台：CT117E-M4 蓝桥杯开发板（STM32G431RBT6）
软件架构：FreeRTOS多任务 + HAL库驱动 + Makefile工程
功能目标：串口控制LED、采集电位器电压、DHT11温湿度、LCD实时显示

【工具链搭建过程】
问题：Keil MDK收费且IDE臃肿，企业实际开发多用VSCode+GCC+OpenOCD
方案：CubeMX生成Makefile工程 + arm-none-eabi-gcc编译 + OpenOCD烧录
踩坑记录：
1. CubeMX自带MinGW路径失效 → 手动下载嵌入式GCC工具链
2. PowerShell路径解析失败 → tasks.json用双反斜杠转义绝对路径
3. make命令找不到rm/mkdir → 用PowerShell原生命令替代
最终效果：Ctrl+Shift+B一键编译烧录，完全脱离Keil

【FreeRTOS多任务架构设计】
任务划分（4个用户任务）：
- StartTask_UART_Cmd（高优先级）：阻塞等待串口消息队列，解析指令
- StartTask_Sensor_Sample（中高优先级）：ADC采集 + DHT11读取，500ms周期
- StartTask_LED_Ctrl（中优先级）：等待LED命令队列，控制锁存器
- StartTask_LCD_Refresh（低优先级）：互斥量保护LCD，200ms刷新周期

RTOS资源使用：
- 2个消息队列：Queue_UART_RX（接收串口数据）、Queue_LED_Cmd（LED控制指令）
- 2个互斥量：mutex_lcd（LCD显示互斥）、mutex_dht（DHT11读取互斥）
- 全局变量：g_adc_val / g_temp / g_humi / g_led_cmd

【串口指令系统设计】
实现方式：USART1中断接收 + 消息队列转发 + 命令任务解析
已实现指令：
- LED_ON / LED_OFF：控制LED8亮灭
- data：查询当前传感器数据（电压+温度+湿度）
- 未知指令：打印[WARN]提示
设计要点：
1. 中断中只负责接收和入队，不做字符串处理（保证中断响应速度）
2. 命令任务优先级最高，保证指令实时响应
3. printf输出加互斥量保护，防止多任务同时打印乱码

【DHT11驱动调试全过程（重点BUG案例）】
第一版问题：驱动中用vTaskDelay(18ms)发送启动信号
→ 原因：vTaskDelay让出CPU，FreeRTOS切换任务，GPIO状态被其他任务干扰
→ 结果：DHT11无法收到完整启动信号，读取永远失败

第二版问题：用taskENTER_CRITICAL()禁用中断
→ 原因：DHT11完整读取需要约21ms，禁用中断太久
→ 结果：FreeRTOS调度器崩溃，系统死机，串口LCD全部无响应

第三版问题：DHT11_Init()中调用osDelay(2000)
→ 原因：osDelay在FreeRTOS启动前调用（main函数中，调度器未启动）
→ 结果：系统直接HardFault，无法启动

最终解决方案：
1. 驱动全程使用DWT硬件周期计数器做微秒延时（不依赖FreeRTOS）
2. 读取时用taskENTER_CRITICAL_FROM_ISR()关中断（约21ms，在可接受范围）
3. Init阶段用自定义delay_ms()（基于DWT，不依赖HAL_Delay或osDelay）
4. Init调用放在FreeRTOS启动后的传感器任务首次循环中

【LCD与LED引脚冲突问题（硬件理解）】
CT117E-M4板子硬件设计：
- PC0-PC7：LCD低8位数据口
- PC8-PC15：通过74HC573锁存器连接LED
- PD2：锁存器使能信号（LE）
- 两组外设共用GPIOC端口输出寄存器（ODR）

问题现象：LCD刷新时LED全部乱闪
根本原因：LCD驱动直接写GPIOC->ODR = value，覆盖了PC8-PC15
修复方案：
1. LCD写数据时用掩码保护高8位：GPIOC->ODR = (GPIOC->ODR & 0xFF00) | (value & 0x00FF)
2. LED操作通过锁存器PD2控制，与LCD数据写入隔离
3. 所有外设操作加互斥量，防止并发冲突

【ADC采集实现】
PA1连接板载电位器，ADC1通道2
采集方式：软件触发单次转换
数据处理：原始12位值 → 0~3.3V浮点电压
printf格式化输出：分离整数和小数部分（避免浮点printf的开销）

三、排查、修复BUG的能力在校招中的价值

【企业底层逻辑】
- 校招不考你能设计多复杂的系统，而是看你遇到问题时的排查思路
- 企业需要的是能独立定位问题、不依赖别人的人
- 面试官通过BUG经历判断你的工程成熟度和抗压能力

【面试讲述标准范式 - STAR-D法】
S（场景）：在什么项目/什么环境下遇到这个问题
T（任务）：你的职责是什么，为什么需要解决
A（行动）：你具体做了什么（重点说排查步骤，不是结果）
R（结果）：最终效果如何，数据量化
D（复盘）：你从中学到什么，后续如何避免同类问题

【可落地BUG素材打造方法】
1. 每次调试记录：现象→假设→验证→结论→收获
2. 积累至少5个不同类型的BUG：硬件连接、时序问题、资源冲突、中断优先级、内存越界
3. 优先选择能体现系统性思维的案例（不是简单接错线）

本周已积累的BUG素材清单：
- DHT11时序问题（FreeRTOS任务切换干扰）
- DHT11初始化问题（调度器未启动时调用RTOS API）
- LCD与LED引脚冲突（GPIO端口共享资源竞争）
- 工具链路径问题（PowerShell特殊字符解析）

五、项目核心复盘结论

本周从零搭建STM32G431 FreeRTOS多传感器采集终端，完整经历了工具链搭建、驱动开发、RTOS任务设计、硬件冲突解决的全流程。核心收获：

1. 工具链是基本功：Makefile+GCC+OpenOCD比Keil更专业，企业实际项目都用这套
2. FreeRTOS不是随便用：初始化阶段不能用osDelay，中断里不能做耗时操作
3. 硬件冲突必须懂：共享GPIO端口的外设要位操作隔离，不能整体覆盖
4. DHT11是经典案例：单总线时序敏感，需要关中断保护，是面试高频考点
5. 调试能力是核心竞争力：printf定位法、假设验证法、最小复现法，比写代码更重要
